# Render 배포·로그인·PvP 랭킹·AI 개발 계획

작성일: 2026-09-29. 현재 기준: `eunjin` / `68b43f3`.
이 문서는 실행 계획이며, 구현·외부 서비스 생성·배포·테스트 완료 기록이 아니다.
이후 구현과 실제 검증 범위는 [구현·검증 기록](render-verification.md), 계정 설정과 배포 절차는 [운영 안내](render-operations.md)를 기준으로 확인한다.

## 1. 확정 범위

- 배포: Render Free Web Service 1개, Singapore 지역을 기본안으로 사용.
- 클라이언트: 기존 Java 8 / Swing 데스크톱 프로그램 유지.
- 예상 부하: 동시 접속 약 4명. 이는 비용·성능 검토용 예상치이며 접속자 4명이나 방 2개를 코드의 상한으로 두지 않는다. 각 방은 1:1이고 접속자·방은 동적으로 관리한다. 4인전 개발은 포함하지 않음.
- 운영 목표: 2026년 12월까지 개발·시연·제출에 사용. 무료 서비스의 무중단 동작을 보장한다는 뜻은 아님.
- 계정·저장소: Supabase Auth + PostgreSQL을 구현 기본안으로 사용.
- 공식 랭킹: 인증된 사용자의 온라인 1:1 PvP 결과만 집계. Story 기록은 공식 랭킹에 포함하지 않음.
- AI: 기존 탐색·평가·비동기 제어를 재사용하고 적응형 정책 1종과 보스 국면 정책 1종 추가.
- 외부 주기 요청, cron-job.org 작업, 자체 절전 방지 타이머는 이번 구현과 배포 설정에서 제외. 제출 시 별도 설정 검토.
- 경기 중 재접속 후 상태 복구, 다인전, 자동 매칭, 소셜 로그인, AI 아이템 사용은 후속 범위.

## 2. 현재 코드에서 재사용할 부분과 변경점

| 영역 | 현재 | 이번 변경 |
|---|---|---|
| 전투 | 서버의 BattleManager가 입력·중력·승패 판정 | 기존 권한 경계와 규칙 유지 |
| 통신 | 루프백 TCP, 길이 지정 JSON, 방·준비·재대결 | HTTP/WebSocket 전송 추가, 배포 환경은 WSS 사용 |
| 세션 | NetworkClient / OnlineMatchSession / SessionUpdate | 전송 교체와 인증·저장 상태를 기존 계약에 연결 |
| 신원 | 연결마다 임시 참가자 ID | 검증된 Supabase 계정 ID와 경기 참가자 ID 결합 |
| 결과 | 메모리 상태만 존재 | 경기 시작·종료 및 랭킹을 DB에 저장 |
| AI | 일반·엘리트·보스 모두 FIXED | FIXED / ADAPTIVE / BOSS 정책 등록 |
| 빌드 | Windows build.ps1, GUI 진입점 JAR | 기존 명령 유지, 서버 진입점·Linux Docker 빌드 추가 |

현재 동작의 기준 문서는 `docs/contracts/g0-contracts.md`, `docs/handoff/ai.md`, `docs/handoff/network.md`다. 이전 Phase 문서의 Adaptive/Mirror 설명을 현재 구현으로 간주하지 않는다.

## 3. 목표 구조

```text
Java Swing 클라이언트
  ├─ HTTPS → Supabase Auth: 회원가입·로그인·세션 갱신
  ├─ HTTPS → Supabase Data API: 허용된 프로필·랭킹 조회
  └─ WSS → Render Java 게임 서버
              ├─ 인증 검증 → 계정과 연결 결합
              ├─ 방/경기 → 기존 BattleManager / GameEngine
              └─ HTTPS → Supabase: 경기 기록·랭킹 갱신 RPC

로컬 Story → 기존 AI worker + 신규 WeightPolicy
```

- Render의 하나의 HTTP 포트에서 `/ws`와 배포 상태 확인용 `/healthz` 제공. `0.0.0.0:$PORT` 바인딩.
- `/healthz`는 상태를 확인하는 짧은 응답만 제공. 외부 호출 예약이나 DB를 깨우기 위한 조회는 연결하지 않음.
- WSS의 외부 TLS는 Render에서 종료. 로컬 개발에서는 명시적인 localhost `ws://` 설정 사용.
- TCP 프레임과 JSON 메시지 검증을 분리하여 기존 DTO 검증 재사용. WebSocket에서는 메시지 경계·크기 제한·분할 프레임도 검증.
- 새 연결은 인증 전 방 생성·입장·입력 금지. 인증 메시지 또는 헤더를 사용하고 URL에 토큰을 넣지 않음.
- 인증 완료 제한 시간과 비인증 연결 수 제한을 별도로 두고 시간 초과 연결을 정리. 비인증 연결이 게임 참가자 슬롯을 계속 점유하지 않도록 검증.
- DB/API 통신과 JWT 키 조회는 게임 tick 및 Swing EDT를 막지 않는 별도 실행 경로로 처리.
- 정상 연결의 ping/pong과 오류 감지는 통신 수명주기 기능으로 구현. 접속자가 없을 때 절전을 막는 작업은 실행하지 않음.
- 1차는 서버 인스턴스 1개로 운영. 방 상태를 가진 서버의 복제·수평 확장은 포함하지 않음.

## 4. 구현 순서와 완료 기준

| 순서 | 작업 묶음 | 산출물 | 완료 기준 |
|---|---|---|---|
| R0 | 현재 회귀 기준과 공유 계약 정리 | 기본 테스트 결과, 인증·결과 DTO, 오류/종료 정책 | 기존 Test 통과 여부 기록, 변경 호출부와 담당 경계 확인 |
| R1 | 빌드·서버 실행 구조 정리 | 의존성 관리, 서버 진입점, Dockerfile, 설정 예시 | Java 8 클라이언트 빌드 유지, Linux 컨테이너에서 headless 서버 기동 |
| R2 | WebSocket 전송 구현 | WS 서버/클라이언트, 공통 방 로직, health 응답 | 로컬 2클라이언트 방→준비→대전→결과→재대결; 기존 TCP 회귀 유지 |
| R3 | Supabase 계정·스키마 구성 | 마이그레이션 SQL, RLS/권한, Auth 서비스, 메일 설정 | 실제 4계정의 가입·인증·복구, 로그인·만료·갱신·로그아웃, 위조 사용자 차단 |
| R4 | 결과 저장·PvP 랭킹 | 경기 시작/종료 서비스, 원자적 결과 RPC, 조회 DTO | 중복 종료·저장 재시도에도 결과와 양쪽 레이팅이 한 번만 반영 |
| R5 | 앱·화면 연결 | 로그인·랭킹 서비스 연결, 접속/저장 상태, UI fixture | 로그인→대전→랭킹 확인→재로그인 후 기록 유지 |
| A1 | 적응형 AI | AdaptiveWeightPolicy, 프로필 등록, 정책 시험 | 관측 부족·극단값에서도 범위 내 가중치, 오류 시 기본 정책 복구 |
| A2 | 보스 AI·비교 검증 | BossWeightPolicy, 국면 시험, 비교 결과 | HP 경계에서 안정적 전환, 동일 조건 비교와 회귀 통과 |
| R6 | 통합·실배포 검증 | render.yaml, 배포 안내, 결과 보고 | Render에서 4클라이언트/2경기, 종료·장애·랭킹 검증 |

R0 → R1 → R2로 배포 가능한 통신을 먼저 확보한다. R3 → R4 → R5는 계정/결과 계약 순서대로 진행한다. A1 → A2는 R0 이후 Network와 독립적으로 진행 가능하다. R6는 두 작업 축이 합쳐진 뒤 수행한다.

기존 간트의 병합 단위에는 1차=서버/통신·인증 초안·적응형 AI, 2차=랭킹·보스 정책·화면 연결, 3차=실배포·통합 회귀·결함 수정으로 대응한다. 실제 개발은 날짜를 기다리지 않고 앞 단계의 완료 기준을 통과하는 대로 이어간다.

테스트 전용 계정/인증 대역은 로컬 시험에만 사용한다. 배포용 설정은 실제 인증이 준비되지 않으면 경기 접속을 닫는 방식으로 실패한다.

### R1: 빌드 기본안

- HTTP/WebSocket은 Java 8 호환 라이브러리를 사용하고 버전을 고정. Netty 4.2 계열을 우선 검증 후보로 선정.
- 의존성 관리는 Maven Wrapper 도입을 기본안으로 하되 기존 `build.ps1 -Task Build/Test/Run/Server` 진입점과 테스트 실행 의미를 유지.
- 기존 main 기반 테스트와 `-ea` 실행을 새 빌드에서도 실제로 수행. 테스트 수집만 되고 실행되지 않는 전환 금지.
- 클라이언트 JAR과 서버 산출물을 구분하고, 서버 전용 비밀 설정을 클라이언트 배포물에 포함하지 않음.
- 의존성 추가 후 Java 8 실행 호환성과 Docker 이미지의 실제 기동을 확인한 뒤 라이브러리 선택 확정.
- Render Free 메모리 안에서 JVM heap·네트워크 worker 수에 여유를 남기고 실제 RSS와 tick 지연을 측정. 처음부터 다중 서버나 서버 내 Story AI를 추가하지 않음.

### R3: 로그인 기본안

- 1차는 이메일·비밀번호 방식: 회원가입, 이메일 인증 안내, 로그인, 로그아웃, 만료·갱신 처리.
- 비밀번호 재설정은 Supabase 복구 링크와 비밀번호 변경 경로를 연결. 네 명의 실제 사용자 주소로 인증·복구 메일을 보낼 수 있는 custom SMTP와 리다이렉트 설정을 R3 실서비스 완료의 필수 선행 조건으로 둠.
- Supabase 기본 SMTP는 현재 프로젝트 조직 멤버 주소에만 발송하고 시간당 2통으로 제한되므로 일반 사용자 가입 기능의 근거로 삼지 않음. 개발 중 메일 대역을 사용한 시험과 실제 사용자 메일 수신 시험을 구분.
- 비밀번호를 자체 DB에 저장하지 않음. 초기 버전은 세션 토큰을 메모리에 보관하고 앱 재실행 시 다시 로그인.
- 게임 서버는 서명·발급자·수신 대상·만료와 사용자 식별을 검증. 검증된 사용자와 연결을 결합하며 클라이언트의 임의 userId를 신뢰하지 않음.
- 같은 계정의 동시 경기 참가와 자기 자신과의 대전 거절. 재인증·갱신 실패 시 종료 이유를 구분.
- 인증 검증 실패와 인증 서비스 장애를 구분하고 토큰·비밀번호는 로그에 남기지 않음.

### R4: 랭킹 기본안

| 데이터 | 책임 |
|---|---|
| profiles | 계정 ID, 표시 닉네임 |
| matches | 경기 ID, 서버 실행 ID, 규칙 버전, 시작/종료 시각, 진행/확정/무효 상태, 종료 사유 |
| match_participants | 경기별 두 계정, 결과, 변경 전후 레이팅 |
| player_stats | 현재 레이팅, 승·패·경기 수, 진행/확정 대기 경기 ID |

- 제안 기본값: 초기 Elo 1000, K=32. 수치는 설정으로 분리하고 결과 반올림 규칙도 고정.
- 랭킹은 확정 경기 1회 이상 참가한 계정 대상. 같은 레이팅은 공동 순위, 표시 순서는 안정적으로 유지.
- 경기 시작 전 DB에 참가자·경기 ID 등록을 완료. DB가 불가하면 랭킹 경기를 시작하지 않음.
- 시작 등록도 두 계정의 행 잠금과 트랜잭션으로 처리. 각 계정의 이전 경기가 확정 또는 무효 상태로 정리될 때까지 다음 랭킹 경기·재대결 시작 금지. 결과 RPC 도착 순서로 Elo가 달라지는 문제를 차단.
- 방 작업 큐에서 STARTING 상태와 참가자·방 버전·서버 실행 ID를 고정한 뒤 비동기 등록. 완료 콜백은 같은 큐에서 해당 시작 시도가 여전히 유효한지 재검증하고, 그때만 실제 경기를 시작.
- 등록 중 이탈·취소·서버 종료가 발생하면 생성된 경기 레코드 무효 처리와 두 계정의 진행 경기 연결 해제를 같은 트랜잭션의 멱등 보상으로 수행. DB 응답이 유실되면 경기 ID로 등록 여부를 확인하고, 정리 전에는 해당 계정으로 새 경기 시작 금지.
- 종료 RPC는 사전 등록된 경기와 두 참가자를 검사하고, 결과·양쪽 통계·레이팅을 한 트랜잭션으로 확정.
- 경기 ID별 중복 방지와 행 잠금을 적용. 이미 확정된 같은 결과는 재시도해도 다시 점수 변경하지 않고, 상충 결과는 거절.
- 클라이언트에는 프로필의 허용 필드와 제한된 랭킹 조회만 제공. 경기 결과·레이팅 쓰기 및 확정 RPC 호출은 신뢰된 서버만 허용.
- 명시적 나가기는 기권. 일반 연결 끊김은 서버가 정상이고 상대 연결이 유효한지 확인한 뒤 정의된 짧은 판정 유예 후 처리. 경기 중 세션 복구는 제공하지 않음.
- 서버 종료·tick 실패·양쪽 연결 단절 등 판정 불가 상황은 무효 처리하고 레이팅 미변경.
- 결과 저장 실패는 화면에 미확정으로 표시하고 제한된 재시도 수행. HTTP 응답 유실 때에는 경기 ID로 DB 확정 여부 조회.
- 서버가 DB에 결과를 확정하기 전에 소실되면 그 결과를 복원할 수 있다고 주장하지 않음. 구 서버 실행의 종료를 확인한 후에만 그 실행에 속한 미확정 경기를 무효 처리하고 계정의 진행 경기 연결을 해제.
- 새 인스턴스가 시작했다는 이유만으로 다른 서버 실행의 경기를 자동 무효 처리하지 않음. 무효 처리와 결과 확정은 같은 경기 행의 잠금·상태 검사로 경쟁을 막고 이미 확정된 결과는 유지.
- DB 확정이 끝난 경기는 서버 재시작 후에도 보존. 메모리 재시도 큐나 Render 로컬 파일을 영구 저장소로 취급하지 않음.

### A1/A2: AI 변경 범위

- 일반은 FIXED 기준을 유지. 엘리트는 공개 플레이 관측으로 허용 범위 내 가중치 조정. 보스는 자기 HP 등 공개 맥락으로 국면 전환.
- 신규 정책 구현뿐 아니라 AIProfileCatalog, MonsterStrategies, profiles.properties 및 FIXED만 허용하던 테스트를 함께 변경.
- 정책 상태는 계획의 입력이 전부 수락됐을 때만 확정하는 기존 규칙 유지. 취소·오래된 계획·부분 거절 때 상태를 전진시키지 않음.
- 보스 HP 경계의 반복 전환 방지와 관측 초기화/이월 규칙 검증.
- 고정 시드·동일 관측·정해진 탐색 한도로 정책 비교. 실행 시간·탐색 중단·fallback을 함께 기록.
- 탐색에 벽시계 시간 예산이 있으므로 같은 seed만으로 완전 결정성을 보장하지 않음.
- 자동 비교는 합성 대전 근거. 실제 난이도 채택에는 사람 플레이 확인을 별도 기록.
- Core의 이동·회전·아이템 규칙이 변경되면 공통 시뮬레이터와 AI 회귀를 다시 확인.

## 5. 파일과 협업 경계

| 위치 | 계획된 작업 | 협업 |
|---|---|---|
| network/, network/server/, network/protocol/ | 전송·방·인증 결합·서버 결과 저장 | 심은진 주도 |
| auth/ (신규), ranking/ (신규) | 계정·랭킹 서비스와 DTO | 심은진 주도, 공개 API 통합 확인 |
| ai/, controller/AIController, ai/profiles.properties | 적응형·보스 정책 및 진단 | 심은진 주도 |
| app/, app/session/ | transport 선택, 계정 연결, 저장 결과 전달 | 통합 담당과 계약 조율 |
| ui/ | 로그인·랭킹·접속/오류 표시 | 조성은과 DTO/fixture 연결 |
| core/, battle/, item/ | 기존 판정 재사용, 필요한 결과 노출만 계약 협의 | 전예랑과 영향 확인 |
| build.ps1, pom.xml/Wrapper, Dockerfile, render.yaml | 기존 개발 명령 유지와 배포 빌드 | 통합 담당과 확인 |
| supabase/migrations/ (신규) | 테이블·권한·RPC와 초기 설정 | 스키마 변경을 코드로 재현 |
| src/test/, docs/ | 변경 계약·실패 경계·실행 안내 | 작업마다 함께 갱신 |

AI와 Network는 독립적인 작업 단위로 나누되 app/session, 빌드 등 공유 파일은 한 통합 작업자가 변경한다. 문서 작성만으로 기존 담당자의 소유권을 이전하지 않는다.

## 6. 검증과 완료 경계

1. **회귀:** 기존 headless 전체 테스트, 컴파일, diff 검사. 실제 창·포커스 검증은 별도 수동 단계.
2. **통신:** 방 입장·준비·대전·결과·재대결, 분할/잘못된 WS 메시지, 중복 요청·구경기 메시지, 크기/속도 제한과 종료.
3. **인증:** 잘못된 토큰·만료·다른 프로젝트 토큰·동일 계정 중복·임의 userId 거절, 비인증 연결 타임아웃/상한, 비밀키 배포물 미포함, 실제 4계정의 인증·복구 메일 수신.
4. **랭킹:** 동일 경기 종료 동시 호출, DB 실패·응답 유실·재시작, 무효 경기, 조회 권한·RPC 직접 호출 거절. 시작 등록 중 이탈·취소, 결과 미확정 상태의 재대결 거절, 구·신 서버 공존 중 진행 경기 보호도 확인.
5. **AI:** 관측 부족·극단값·HP 국면 경계·범위 초과·정책 오류·취소·상태 확정, 기존 합법 입력 경로 회귀.
6. **실서비스:** 예상 부하인 4클라이언트/2경기를 서로 다른 PC에서 동시에 실행하고 지연·서버 메모리·입력 누락·방 간 간섭을 측정한다. 로컬 회귀는 예상 인원을 넘어서는 접속과 방 생성도 확인한다.
7. **종단 완료:** 로그인 → 대전 → 서버 판정 → DB에 한 번 확정 → 랭킹 갱신 → 앱/서버 재시작 후 확정 기록 유지.

로컬 테스트 통과, Docker 기동, Render 배포 성공, 인터넷 대전 검증, 사람 대상 AI 밸런스를 각각 구분하여 보고한다. 예상 접속 4명은 제품 한도가 아니며, 실제 배포 성능은 부하 시험으로 확인한다. 소켓·인증 대기 등 운영상 자원 보호 한도는 예상 인원과 분리하여 설정한다.

## 7. 배포 준비와 제출 시점 작업

### 구현·통합 중 준비

- Render/Supabase 계정과 프로젝트, 실제 URL·공개키·서버 비밀키를 확보. 비밀값은 환경 설정으로 주입.
- Render 서비스는 Free 1개, Singapore 기본안, Docker, PORT, 서버 시작 명령, health 경로 설정.
- Supabase 마이그레이션 적용, 이메일 인증/복구 설정, 서비스 상태 확인.
- 자동 배포를 끄고 수동 배포로 운영. 운영자 인증을 요구하는 drain 제어로 새 경기 시작을 닫고, 기존 경기와 결과 저장이 모두 정리된 것을 확인한 후 구 서버를 정지하고 배포.
- 새 버전은 기본적으로 경기 접수가 닫힌 상태로 기동. 구 실행 종료 확인·미확정 경기 정리·준비 상태 확인 후 접수를 재개. 즉시 재시작이 발생했을 때도 같은 절차로 복구. Render의 배포 중 구·신 인스턴스 공존을 고려하며 다른 살아 있는 실행의 상태를 정리하지 않음.
- 로컬 개발/배포 환경 설정과 클라이언트 배포 패키지 준비. 기본 코드에 실제 비밀값 저장 금지.

### 제출 시 별도로 검토

- 사용자 요청에 따라 외부 주기 상태 요청의 정책·도구·종료일을 다시 확인하고 그때 설정.
- 현재 코드·CI·render.yaml에는 유휴 절전 방지용 예약 작업을 넣지 않음.
- 무료 서비스의 초기 기동 대기, 재시작과 할당량, Supabase 비활동 일시중지 확인.
- 실행 파일, 서버 주소, 테스트 계정 안내, 검증 결과, 설정 재현 방법을 제출 자료로 정리. 문서에 계정 비밀번호를 넣지 않음.
